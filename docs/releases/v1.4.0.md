**One jar per Minecraft version, from 1.21.2 all the way to 26.2.** Until now this mod existed only
for 26.2; the twelve jars attached below are the same mod built for every version it supports.

### Which jar do I want

Take the one whose name matches your Minecraft version — `hidemodels-1.4.0+mc1.21.8.jar` for 1.21.8,
`hidemodels-1.4.0+mc26.2.jar` for 26.2 — and drop it into `mods/`. There is no universal jar on
purpose: each one declares the version it was built for, so Loader refuses the wrong one up front
instead of letting it fail somewhere later.

Requirements are unchanged and still modest: Fabric Loader `>=0.19.0`, Java 25 on 26.x or 21 on
1.21.x, **no Fabric API**, no other mods, and nothing at all on the server — it is client-only.

### What is new

* **1.21.2 – 26.2 support** from a single source tree. Exactly one file differs between the old and
  new versions (the client-side chat call, renamed in 26.x); everything else compiles unchanged.
* **The model component is found by id rather than by name**, which is what makes that range
  possible. A side effect worth knowing: on 1.21.1, where `item_model` does not exist, the mod falls
  back to `custom_model_data` — it runs, but the ids you would write are different ones.
* **Configuration and behaviour are unchanged.** `config/hidemodels.txt` and the `/hidemodels`
  command work exactly as they did in 1.3.0; upgrading is just swapping the jar.

### How much of this was actually tested

Every one of the twelve jars is launched in a real Minecraft client in CI, on every push — not
merely compiled. That run checks that the model component still resolves out of the registry on that
version and that editing the config still drives what gets hidden.

Four of those versions go further and run a full client gametest, which builds a world, spawns an
entity carrying an `item_model`, and asserts the mod reads it, intercepts its command and honours
its config. It covers 1.21.4 through 1.21.8 in CI and works locally on 1.21.9+ as well; the
limitation is a hosted runner's, not the mod's, and the README explains it.

On top of that, every mixin target and every vanilla type the mod names is checked against each
version's own client jar, so a method Mojang renamed is caught before release rather than at
someone's startup.
